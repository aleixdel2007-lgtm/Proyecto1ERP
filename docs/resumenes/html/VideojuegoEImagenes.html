La idea en una frase

En la base de datos no hay ni un byte de imagen. El archivo se escribe en una carpeta del servidor con un nombre inventado, y en la tabla solo se guarda la ruta para poder encontrarlo. La base lleva los datos; el disco, los archivos.

1En 30 segundos
  1. Primero se guarda la ficha del juego —título, precio, PEGI, categorías y plataformas— y la fila recibe su id.
  2. Las imágenes se suben después, una a una, eligiendo si es portada, banner o captura.
  3. El servidor comprueba el tipo y el tamaño, y que no haya ya una portada o un banner: de esos solo cabe uno.
  4. El archivo se escribe en uploads/videojuegos/<id>-<slug>/ con un nombre inventado (un UUID), nunca con el nombre que traía.
  5. En la tabla imagen_videojuego se guarda la ruta, no la imagen. Si la fila falla, el archivo recién escrito se borra a mano.
  6. Al pintar la ficha, el navegador pide esa ruta y WebConfig le sirve el archivo desde la carpeta.

4Los conceptos que toca

Diez ideas de las que se estudian en clase, con el sitio exacto del proyecto donde están aplicadas. El color del borde dice de qué familia es cada una: diseño, seguridad, base de datos, robustez.

01 · Diseño

La ruta en la base, el archivo en el disco

Guardar imágenes como BLOB engorda la base, hace lentas las copias de seguridad y obliga a que cada imagen pase por la aplicación. Con una ruta, el servidor web la sirve directa y el navegador la guarda en caché.

imagen_videojuego.ruta · VARCHAR(255)
02 · Seguridad

El nombre lo pone un UUID

El nombre que trae el archivo del usuario nunca forma parte de una ruta: podría llevar ../, caracteres raros o repetirse. Se tira y se pone un identificador aleatorio.

UUID.randomUUID() + "." + extension
03 · Seguridad

No salirse de la carpeta

Antes de leer o borrar nada se normaliza la ruta (que resuelve los ..) y se comprueba que siga empezando por la carpeta base. Es la defensa contra el path traversal.

archivo.normalize().startsWith(base)
04 · Seguridad

Validar formato y tamaño en el servidor

Solo pasan png, jpg y webp, y como mucho 2 MB. El accept del formulario es una comodidad; quien manda es esta comprobación.

AlmacenArchivos.extensionDe
05 · Seguridad

Público y privado en carpetas distintas

Las imágenes van en uploads, que se sirve entero como web. Los ZIP de los juegos van fuera, y solo se entregan por un controlador que antes comprueba si tienes una clave.

app.uploads.dir vs app.juegos.dir
06 · Diseño

La carpeta se busca por id, no por nombre

La carpeta se llama <id>-<slug>, pero se localiza buscando el patrón <id>-*. Así renombrar el juego no obliga a mover nada de sitio: el slug es decoración, la identidad es el id.

buscarCarpeta(videojuegoId)
07 · Diseño

Convertir un título en nombre de carpeta

El slug quita acentos, pasa a minúsculas, cambia lo raro por guiones y recorta a 40 caracteres, por el límite de 260 de las rutas de Windows. Un título solo de emojis se queda en juego.

AlmacenArchivos.slug(titulo)
08 · Robustez

El disco no tiene rollback

Si la transacción se deshace, la fila desaparece pero el archivo sigue ahí. Por eso el código lo borra a mano en el catch: lo que la base hace sola, en el disco hay que compensarlo.

catch (RuntimeException) { almacen.borrar(ruta) }
09 · Base de datos

Borrar en cascada… solo las filas

Al borrar un juego, cascade = ALL se lleva sus filas de imagen. Los archivos no: hay que llamar aparte a borrarCarpeta(), o quedan huérfanos ocupando sitio.

@OneToMany(cascade = ALL, orphanRemoval = true)
10 · Diseño

Servir una carpeta como si fuera web

Las imágenes viven fuera del .jar, así que no son recursos de la aplicación. WebConfig engancha la URL /uploads/** con esa carpeta del disco.

registry.addResourceHandler("/uploads/**")
5Las dos preguntas de examen

¿Por qué no guardar la imagen en la base de datos como un BLOB?

Porque la base dejaría de ser manejable. Unas pocas miles de portadas la hinchan a varios gigas, y eso hace lentas las copias de seguridad y caras las restauraciones. Además, cada vez que alguien abriera una ficha, los bytes tendrían que viajar de la base a la aplicación y de ahí al navegador, gastando memoria y conexiones para algo que un servidor web hace directamente y mucho mejor. Con una ruta, la imagen se sirve como un archivo estático, el navegador la guarda en caché y no vuelve a pedirla. La regla general: la base de datos para datos que se consultan y se relacionan; el disco para archivos que solo se entregan tal cual.

¿Qué pasa si el archivo se escribe pero falla al guardar la fila?

Que tendrías un archivo huérfano: ocupando espacio y sin que nadie sepa que está ahí, porque nada lo apunta. La transacción de la base deshace la fila sola, pero el sistema de archivos no participa en ella y no sabe deshacer nada. Por eso el servicio envuelve el guardado en un try y, si salta la excepción, borra el archivo antes de relanzarla. Es compensar a mano lo que la base hace automáticamente, y es el precio de tener los datos en dos sitios que no se coordinan entre sí.
